# 路长官对无地头衔人物的原生审批测试

## 当前范围

当前原生拘捕组10项／75断言，其中批准用例8断言、否决用例7断言；另有独立观察证据用例8断言。全组110项／485断言。正式审批队列、即时收押和后续观察分开验证。

单项入口为`event tca_judicial_arrest_test.<编号>`：

- `.1`／`.2`：在任提刑兼持世族头衔，确定否决／批准。
- `.3`／`.4`：发送时在任提刑不持世族头衔，确定否决／批准。
- `.5`／`.6`：仅持世族头衔，确定否决／批准。
- `.7`／`.8`：其他公国级无地官职兼持世族头衔，确定否决／批准。
- `.9`／`.10`：其他公国级无地官职不持世族头衔，确定否决／批准。

各项独立运行司法准备，从当前有效且未被本组测试使用的路中选取所测路，创建新AI路长官并转任，建立与皇帝的实际隶属；创建自己的目标和真实下属关系，不切换玩家，不继承前项请求冷却。世族通过原生give_noble_family_title创建，普通无地官职通过create_dynamic_title、资本设置、set_landless_title和任命事务创建，不伪造提刑标记。身份、管辖、审批角色和资格直接使用正式实现。

无世族对照仅要求**发送时**没有世族头衔；若原生授职自动生成世族，仅销毁该测试人物的世族头衔。后续自然提刑维护可能补回世族，不把“永久没有世族”作为前提。每项会替换测试世界的路长官或提刑，不能在正常存档运行。

## 原生发送与控制

`common/scripted_effects/tca_judicial_arrest_test_effects.txt`通过正式`tca_request_imprison_interaction`的run_interaction发送，设置send_threshold=decline，**不设置execute_threshold**。禁止用execute_threshold=accept：该路径会直接执行OnAccept，不能测试审批队列。

原版依据：release/1.20.0、Exe Git 22725d4504；events/dlc/ep3/ep3_interactions_events.txt约3099行以send_threshold=decline发送普通拘捕，events/diarchy_events/diarchy_events.txt约808行展示actor／recipient接口。只读检查CRunInteractionEffect构造函数0x104bea498—0x104bea49c，两个threshold默认值为3；ExecuteDerived在0x104beaefc—0x104beaf08的execute分支直接OnAccept，而0x104beafa4—0x104beafd8的send分支执行CSendCharacterInteractionCommand。本组只启用后者，进入玩家发送按钮使用的同一manager。

新路长官用原版schemed_against_me取得合法拘捕理由，满足正式AI发送条件。正式ai_intermediary_accept加入两个仅测试modifier：debug模式且发起者带tca_test_arrest_force_veto时−1000，带tca_test_arrest_force_approval时＋1000。标记只由一次性测试路长官取得，结束时清除；正常请求评分不变。测试路长官创建时谋略100，并取得原版prison_feudal_complex_perk；目标谋略1且无随机性格，以隔离审批与目标拒捕的结果。

正式on_send及审批接受／否决、目标接受入口加入debug观察钩子，仅对带tca_test_arrest_native_active标记的测试路长官计数。tca_test_arrest_sent／approved／vetoed／target_accepted是独立角色变量，不改写框架统计，也不批准、收押或重定向角色。没有真实发送就不能凭“目标仍未入狱”通过。

## 即时回归与后续观察

1. 实际AI路长官、无地目标、隶属、官职和发送时世族有无符合场景。
2. 正式角色构建得到有效AI审批人，正式拘捕资格及原生is_character_interaction_valid通过，随后真正发送。
3. 发送当下sent=1，批准／否决／目标接受计数均为0，目标未入狱。
4. 次日仍等待，不能立即抓人再补审批；正式ai_min_reply_days为4。
5. 第20日：批准场景恰有1次批准及目标接受、0次否决；否决场景恰有1次否决、0次批准及目标接受。
6. 批准场景第20日的状态与本项收押、释放或死亡证据一致；否决后仍在狱外。
7. 否决的三项正式好感修正存在；批准场景没有误加否决好感修正。
8. 批准场景记录了本项实际收押当下的正确关押者与无公职囚犯登记。

20日覆盖正常两阶段4—9日等待上界。否决资源数值沿用既有回复测试，不用20日后余额反推扣款，避免自然资源收入干扰。

## 运行与失败解释

用户重启专用1066中国debug测试局，运行测试决议或event tca_tests.1，并继续推进至最终通知。新增10项每项20日，串行增加200个游戏日；单项也推进20日，不并发启动另一项。新组位于原有九项延迟之后，结束后才汇总。

原有等待、批准／否决、关押及意见断言全部保留。修复前已取得绕过审批的失败证据；修复后仍须从真实发送入口核对，不删除或放宽断言。

断言1／2失败先处理场景或发送接口；sent=0表示未验证真实发送；缺第20日结果表示未完成。使用tools/check_test_run.py核对当前110项／485断言和同次error.log。最新执行结果见本页当前验收；界面、人工审批与保存重载仍待单独验收。

## 未覆盖的无地类型

本组没有把普通无地官职伪装成教区或枢机。原自动接受还包含clerical_elector_title与has_clerical_region分支，1066中国尚未构造这些真实宗教机构，不能声称已覆盖全部无地类型。补充验收须使用真实有效的宗教头衔目标，先确认实际所属路和正式发送资格，再由玩家审批者分别否决／批准，检查未经批准不入狱。确认界面、人工回复、跨版本宗教接口及存读档均不由本组替代。

## 当前观察契约

当前回归不再控制原版AI释放／处决。五个完整互动覆盖及其基线已删除，CLI仅负责启动独立局和执行同一正式测试入口。

- 批准的第8断言继续核对真实收押当下的实际关押者及无公职登记；第5断言核对审批／目标回应计数。
- 批准的第6断言由“第20日必须仍在押”明确改为“收押已证实，且第20日状态有一致追踪证据”。在押必须仍由请求者关押且无公职登记；已自由必须有原关押者的实际出狱回调；已死亡必须有原生死亡回调。无回调的状态丢失或未确认转移仍失败。
- 有出狱／死亡回调不等于已解释原因。原始第20日状态日志继续记录，出狱原因未知须单独报告；先前赎回和死亡导致的失败记录保留为历史，不声称其规则原先就正确或所有原因已确定。
- 否决用例的未收押检查不变。没有重新收押、禁用AI、删除失败场景或放宽即时收押预期。

新增原生`tca_arrest_observation_test.1`及隔日`.1001`，8个断言自建临时角色，使用真实imprison、release_from_prison和death：未收押反例、在押正例、出狱回调／原关押者、出狱追踪一致性、死亡回调、死亡追踪一致性，以及保留另一囚犯的旧释放／死亡证据后，当前囚犯仍必须因缺证据而拒绝的两个反例。只准备自己的审计变量，不修改框架保留统计或运行标记。串行登记为第21项延迟测试，全组110项／485断言。

每个目标携带固定且唯一的`flag`用例标识。真实收押、释放和死亡回调将该标识写入请求者的独立变量列表；释放还核对实际原关押者。后续断言只查本项标识，不借用同一请求者对其他囚犯的旧证据，死亡分支也不读取死者变量。观察用例故意保留前两位囚犯的旧证据，再对未启用观察的第三位囚犯执行释放和死亡，验证两种缺证据情况均被拒绝。
