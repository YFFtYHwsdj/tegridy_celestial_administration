# 开发与文档维护

本页拥有开发流程、文档分工及运行证据保存规则。项目边界见[工作约定](../../AGENTS.md)，模块关系见[架构导航](../../ARCHITECTURE.md)。

## 从任务进入文档

1. 从架构导航找到模块 `README.md`，先了解当前行为、正式入口、兼容边界和未验证事项。
2. 只在任务需要时读取设计、验证说明与历史；历史报告不能作为当前实现的默认上下文。
3. 修改行为时同步修订该模块当前说明；共享接口变化同时更新调用约定和相关消费者。
4. 完成后报告实际改动、执行过的检查、失败与剩余限制。没有源码或测试范围依据的“已验证”不得沿用。

## 文档职责

- 根 `README.md`：稳定的项目介绍、加载与参与入口，不登记功能进度。
- `AGENTS.md`：必须遵守的边界、核心规范和常用验证命令；详细流程通过链接读取。
- `ARCHITECTURE.md`：模块关系和入口，仅在边界、依赖或入口变化时更新，不维护测试计数与功能状态。
- `docs/<module>/README.md`：当前规则与实现入口。小模块一页足够，变长再按实际职责拆分。
- 模块 `design.md`：设计目的、关键取舍和未实现范围，不复制完整脚本或另一份数值表。
- 模块 `verification.md`：可复现步骤、自动与人工验证边界；记录范围和证据指针，避免重复运行明细。
- `research/`：历史问题、史料与采用判断，遵守独立[考证规范](../../research/standards.md)。
- `docs/history/`：有长期维护价值的已终止实验与历史索引；默认不作为待办或当前设计。

同一规则、数值、接口和状态只有一个主要维护位置，其余位置链接引用。文档使用中文，相对链接应在仓库内有效；稳定技术标识和原版术语保留原样。结构化元数据只在确有工具消费时引入，不要求每页填写作者、复审日期或评分表。

数学与平衡研究源码应随库维护。功绩相关统一放在[tools/merit_research](../../tools/merit_research/README.md)，后续研究沿用这一入口；模型检查验证数学假设与守恒，不作为游戏业务规则的第二份正式实现，也不替代原生测试。研究的运行结果、日志及源码冻结副本仍按下述证据规则保存于仓库外。

## 何时保留决策与计划

涉及引擎限制、重大兼容取舍或跨模块接口时，在相关模块的设计页记录背景、决定、理由、后果和状态。被替代的决定明确链接到替代方案。无需每次修复都新建 ADR 文件。

复杂未完成任务可在模块内使用 `plan.md`：记录目标、尚未完成的工作、阻塞、下一步及必要证据。完成后将长期结论并入正式说明，删除重复计划；仅有重要历史理由时归档。不要因为工具或技能默认路径而生成永久流程文档。

## 测试证据如何保存

测试源、框架契约、可复现验收方法随代码入库。每轮运行的日志、结果、截图和冻结源码保存在仓库之外，不要求新增一篇 Markdown；普通验证结果写进当次提交／PR说明或任务交接。

长期文档只保留会影响当前维护的结论：引擎限制写进设计理由，未解决问题写进对应模块的验证说明，明确触发场景、预期／实际差异、正式测试入口和复核方法。普通通过次数、旧断言总数、孤立运行ID和完整执行流水不再整理成独立文档。

发布验收或重要人工结果需要留证时，关联源码提交／内容摘要、游戏版本、执行范围、结果和未覆盖项，并引用仓库内的最小复现材料，或读者可访问的稳定PR、发布附件等共享产物。未提交源码用冻结摘要标识，不能用提交SHA冒充当次源码。没有保存原始产物的旧结论只能作为历史线索，明确待复核，不能继续称为可核验的证据。

本机临时目录、个人绝对路径、个人目录中的文件及只能在当前电脑解析的运行ID，不作为长期文档引用。路径存在也不代表其他维护者可以读取。原始日志、冻结副本和任务元数据保留在运行产物中，不抄进模块文档；本机任务交接可以使用运行ID，但不将其升级为公共知识入口。

当前运行器默认使用系统临时目录，没有自动上传、归档或清理。需要保留产物时显式指定仓库外持久目录：

```sh
python3 tools/run_game_tests.py --timeout 600 \
  --run-root "<仓库外持久产物目录>"
```

将占位符替换为本次环境中的实际目录；环境路径只出现在本次执行配置或产物中。长期共享的证据应另外发布到稳定位置，普通本地目录不构成共享档案。清理前确认没有未解决问题依赖唯一产物；保留期限由实际交付需要决定，不为普通运行制定额外的入库流程。

## 修改前后检查

```sh
# 统一静态回归：包含当前仓库文档检查和工具／文件契约测试
python3 -m unittest discover -s tools -p 'test_*.py'
# 只检查文档时可单独运行
python3 tools/check_docs.py
```

统一静态回归中的 `RepositoryDocumentationChecks` 直接检查当前仓库，检查器自身另有故障样例测试；不只验证临时样例。该检查不依赖游戏启动。

文档工具检查根Markdown、`docs/`及`research/`中的本地行内链接／引用定义、ATX标题锚点和文档模块入口；链接检查忽略代码示例及外部URL，不请求网络。公共根文档及 `docs/` 额外检查个人／临时绝对路径，代码示例也受此约束；`research/` 原始来源记录不作此迁移。工具不验证外部来源可用性、任意代码路径或行为说明与实现的一致性；这些仍需审阅。

- 文档及注释整理：检查本地链接、失效锚点、旧路径、重复／矛盾状态和差异空白；涉及源码注释时确认可执行内容不变。
- 原版覆盖：运行[上游检查](upstream.md)，人工审阅差异，不自动刷新基线。
- 工具逻辑：运行相关 Python 回归；游戏行为直接维护原生测试，详见[测试框架](../testing/framework.md)。
- 纯文档不机械新增业务断言、不为文件移动重跑游戏；不得将文档检查称为新增引擎验收。

普通改动原地修订当前说明，不再按日期追加“本次改动／提交前复核”流水。代码附近的安全调用信息按[注释规范](comments.md)维护，跨文件流程留在模块文档。

## 行为变更的文档审阅

完成行为变更时，从模块入口逐一对照改到的正式入口、规则及限制，审阅相邻调用约定和受影响消费者。修改者应指出主要维护页；审阅者检查是否仍保留旧行为、复制了第二份数值或把未运行项写成已通过。链接检查只能兜底结构错误，不能替代这一步。

重要决定在所属模块写明当前采用的方案、理由、适用条件及何时重新评估；旧引擎观察与当前决定分开。人工验收写准备条件、操作、预期和未覆盖项，场景未准备或随机分支未出现时保留未执行状态。验证结果只在实际执行后记录，不以完善验收说明代替验收。
