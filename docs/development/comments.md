# 代码注释维护

## 目的与分工

注释应让维护者在代码附近理解对象职责、调用约定和容易误改的约束。模块文档说明完整设计、跨文件流程、原版依据及验证记录；两者不能互相替代。注释描述当前实现，不能把设计意图或静态推断写成已验证的引擎结论。

## 写法

- 说明性注释统一使用中文，覆盖游戏脚本、GUI、测试及 Python 工具的文件头、行内注释和 docstring。对象标识、参数名、路径、命令及必要的原版术语保持原样。
- 沿用原版实现的说明也译为中文；需要保留的英文原句附中文解释。原版审阅基线、外部源码快照、测试原文样例不翻译，以保留证据与测试输入。维护既有代码时同步处理本次涉及的英文说明，不维护重复的中英两套注释。
- 文件头说明本文件在机制中的职责。共享对象说明当前作用域、必需参数或 saved scopes，以及重要输出和副作用；简单包装、同类常量可共用分组说明。
- 条件说明业务边界，数值说明计分对象、互斥或累加关系、截断与归一化；调参依据不明时不补写历史理由。
- 生命周期说明状态由谁设置、谁读取、谁清理，哪些关系或序号必须一致，以及哪些绑定应保留。
- 原生回调说明接线与执行时机；复杂的事务顺序、延迟和防重入说明原因。只知道脚本安排时，不据此断言引擎回调先后已被证明。
- 互动区分显示、发送、效果预览和真实执行；测试说明业务场景、预期及等待所覆盖的阶段，避免逐条复述数字断言。
- 生成文件在生成端维护中文来源和入口说明；原版复制内容保留必要的说明含义并译为中文，补充本模组变更点。

例如详覆清理效果应说明“仅清理角色关系和请求序号均匹配的请求，防止旧超时事件清掉新请求”，比“删除变量”更有用。具体状态名及调用约定仍以相邻脚本为准。

## 检查方式与验证边界

纯注释修改应比较修改前后的脚本 token，确认字符串、标识、运算符和顺序不变；同时检查 UTF-8 BOM 与空白错误。生成文件头须同步修改生成工具，并运行相关工具测试。修改已登记覆盖文件时照常运行原版覆盖检查，不刷新基线。
