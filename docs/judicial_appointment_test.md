# 提刑首任与原版继承验证

2026-10-09。当前已删除自定义提刑继承法，本阶段不添加官职专属继承法。

## 当前继承方式

提刑角色使用原版 `celestial_appointment_succession_law`（天朝文官领地继承法），其原版任命类型为 `celestial_civic_governor`。在首次授予、家族初始化和直属路关系变更结束后，检查该角色是否已有此领地法；没有则使用原版 `add_realm_law_skip_effects` 设置。只对主要头衔为本 mod 提刑头衔、非独立且属于天朝政府的角色执行，不修改路领主或皇帝的法律。

没有自定义候选池或评分。贵族家族头衔保留原版独立的世族继承法。后续功绩继承不排除历史人物；首任筛选与正常继承是两个入口。

## 首任补位

候选池包含同一天朝内皇帝及各级封臣的廷臣与无地封臣本人；排除已登记的历史角色、现任部长和公国级以上角色。要求存活、无地、至少原版公国功绩等级门槛（当前 3），并符合原版部长基础与性别资格。按 `1＋学识` 加权抽选。

无合格人选时使用原版文官学者模板生成角色，采用路领主文化、信仰、礼制，补给公国起始功绩并初始化考试履历。低出身角色先创建王朝，再初始化天朝贵族家族。授予官职后设置天朝政府，最后以独立效忠事务归属绑定的当前路持有者。

维护不替换在任官员，会修复缺失家族和直属关系。提刑头衔获得后延迟一天维护，可覆盖初次授予及继承。路领主换任后复用原官职并更新直属关系。

## 历史人物保护

`tca_historical_character_registry.txt` 从本机原版及生成时启用 mod 的历史角色定义提取 ID；每存档登记一次存活历史角色。王安石在排除名单内。未来更换历史角色文件或版本时需更新登记文件与版本；不覆盖登记后才出现的历史角色。该过滤不自动撤换已有历史官员。

## 查看与验证

重启后可在 debug 模式执行“测试空缺提刑首次任命”维护旧存档。“查看提刑头衔”只读报告在任者、政府、实际直属领主，以及提刑司自身是否为 appointment 继承、是否存在 current_heir。人物卡第一继承人不能代替官职头衔自身的诊断。

已有截图证明部分实例可授予官职并直属对应观察使；领地继承页已显示原版天朝任命继承及候选人。此前“专用法缺失”提示已删除。当前沿用原版领地法的改动仍待重启游戏验证；死亡继承、读档和换任后稳定性未完整验证。

曾手动添加自定义提刑法的测试存档，其残留法律如何被引擎处理尚未确认；使用新测试开局最便于验证当前行为。不要把旧截图中专用法的可添加状态当作现阶段要求。

## “无继承”的界面判定

新截图明确显示头衔自身采用 appointment 且 current_heir 为王安石，政府与直属路关系也正确，但头衔窗口显示“无继承”。原版 game/gui/window_title.gui:2319 仅在 Title.IsDestroyedOnSuccession 为真时显示 TITLE_VIEW_SUCCESSION_NONE，正常继承区块则在其为假时显示。当前启用的其他 mod 没有 window_title.gui 覆盖。故不应继续把该表现归因于候选池不存在。

创建、首次授予完成、普通维护完成与延迟继承维护完成均显式 set_destroy_on_succession = no。动态头衔的引擎默认或其他初始化是否导致此前判定为真，尚未得到逐步记录；该属性修复仍需游戏内确认。如果修复后仍显示“无继承”，需继续区分 GUI 的复合引擎判定与此单一销毁属性，不能直接覆写界面隐藏真实状态。

## 2026-10-10：直接读取界面继承销毁判定

“查看提刑头衔”新增只读通知，针对绑定的提刑头衔保存作用域 `tca_viewed_title`，在本地化中使用 `[Select_CString( tca_viewed_title.IsDestroyedOnSuccession, 'true', 'false' )]` 读取与原版头衔窗口相同的 Title 数据函数，同时显示 `IsValid`。不使用猜测的脚本 trigger，也不把 current_heir 或 set_destroy_on_succession 的设置推断为该函数的返回值。

“测试空缺提刑首次任命”通过共用查看流程报告维护后的当前值。维护本身仍会补空缺、修复政府及归属、设置原版领地法与 set_destroy_on_succession = no；只读诊断不会额外修改这些状态。

重启加载修改后，先执行“查看提刑头衔”记录当前值；如需比较维护影响，再执行任命测试并查看新的通知。true 对应原版窗口“无继承”区块，false 对应正常继承区块。本地化表达式在通知显示时求值，不在同一决议中发送所谓“维护前”的通知，以免延迟渲染实际读到维护后的状态；历史通知也不应当作持久属性快照。

值留白、表达式原样显示或 error.log 出现解析错误都不能算读取成功。此数据函数已在原版 GUI 中确认存在，但从通知本地化调用的实际效果仍需游戏内验证。

## 2026-10-10：修复销毁判定并显示实际继承法

本机 CK3 1.20.0.4 的 ARM64 和 x86_64 函数核对表明：`set_delete_on_destroy` 写入头衔字段 +0x36，`set_destroy_on_succession` 写入 +0x35；`CLandedTitle::IsDestroyedOnSuccession` 首先检查 +0x36，非零即返回 true。因此常驻提刑不应保留 delete_on_destroy = yes，即使 destroy_on_succession = no。

新建、既有头衔维护、首次授予完成及延迟获得维护均显式设置 `set_delete_on_destroy = no` 和 `set_destroy_on_succession = no`。主动撤销仍先解除绑定，在紧接着调用 destroy_title 前临时设置 delete_on_destroy = yes，使显式废置或失效清理仍删除动态对象；普通维护不会设置为 yes。

两项现有决议共用的查看流程新增“当前继承法”通知，使用原版头衔窗口的 `Title.GetSuccessionDescription` 读取官职实际继承描述；另显示持有者的 succession_order_laws、succession_gender_laws 名称和头衔 HasLaws。领地法不冒充头衔专属法，旧存档残留专属法时以上面的实际描述为准。空缺官职不读取不存在的持有者法律。

重启后先执行“查看提刑头衔”记录旧状态，再执行“测试空缺提刑首次任命”修复已有对象，查看继承销毁判定是否变为 false、实际继承法是否为原版天朝文官任命。候选人和法律通知都不是死亡交接已经成功的证据；后续须在测试存档验证死亡继承、保存读取以及主动废置与恢复。新增法律通知和修复的游戏内效果待验证。
