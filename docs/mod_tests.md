# 模组游戏内测试

## 当前结构

测试直接维护为CK3原生隐藏事件，不使用Python生成器，也不保留另一套P脚本中间源。`events/`下的测试文件就是正式测试代码，`common/scripted_effects/tca_judicial_law_test_effects.txt`是共享场景准备，Python仅用于读取日志和静态检查。

官制13项、司法法律42项、加载／命名3项、真实延迟4项，合计62项／242个断言。前三组58项即时检查，四项延迟共有10个断言，分别检查次日维护、关闭司法、启用司法和死亡后的补位／公职囚犯交接。业务条件和断言未删除或放宽。

## 运行和维护

重启专用1066中国debug局，用“调试：模组一键测试”或`event tca_tests.1`运行；取消暂停推进至少八日，直到最终通知。单项入口沿用各组事件ID。测试会修改世界，不使用正常游玩存档。测试期间不切换玩家或并发启动。

直接编辑`events/tca_*_test_events.txt`。每项自备前置和状态，调用正式trigger/effect，通过if／limit检查结果；日志保留唯一tca_test_名称、连续CHECK编号及BEGIN／PASS／FAIL／PRECONDITION_FAIL。前置不满足计未执行，任何失败保留到用例结束。不要改写统计值来制造通过。

真实等待写成原生trigger_event的days参数，由后续角色事件检查。续接事件保留上下文，四项串行运行，不以直接调用正式worker替代自然触发。请求角色死亡、事件丢失或退出游戏时，无最终结果就是未完成。

新增用例在总入口`events/tca_tests_events.txt`登记并同步计划数量；延迟调度在该文件和`tca_test_delayed_dispatch_effects.txt`维护。日志工具从正式事件读取预期用例和编号，工具回归检查登记、连续编号和总数量。没有生成步骤。

检查命令：`python3 -m unittest discover -s tools -p 'test_*.py'`；游戏运行后用`python3 tools/check_test_run.py`，并审阅同次error.log。源码及静态通过不能当作引擎结果。

## 当前入口

启用 debug 模式后，点击调试决议分类中的“调试：模组一键测试”，或在控制台输入 `event tca_tests.1`。两者调用同一个总入口，先运行即时用例，再串行运行延迟用例。等待期间显示“等待中”，需取消暂停并推进日期；最后一项结束才显示汇总结果。旧命令 `event tca_court_test.100` 保留为总入口别名。

上方 toast 通知显示“全部通过”或“未全部通过”，以及通过、未通过数量；不再打开需要关闭的事件窗口。未通过数是计划用例数减通过数，包含断言失败、前置不满足的未执行，以及未完成的用例。失败通知补充失败和未执行数量，详情在 debug.log 的 TCA_TEST 行中。每项任意 expect 失败就计为一个失败用例，不按断言个数累计。

决议只在调试模式下对玩家显示，AI 不运行。总入口也检查 debug 模式。各测试自己检查场景条件，场景不合适时计为未执行，不阻止其他测试组执行。目前已登记3组59项：13项[官制测试](court_system_engine_tests.md)、42项即时[司法法律测试](judicial_law_tests.md)及4项延迟司法测试。当前两组使用专用1066中国及无外部官名管理场景；司法组还需至少两位普通文官路主官，个别用例要求属州、县官或军制／都护对象。不满足前置记未执行，不能当作通过。未来其他组可有不同前置条件。

测试会修改世界状态，使用专用测试局；通知仅统计脚本断言，不能自动证明 error.log 没有引擎脚本错误。全部断言通过后仍核对错误日志。外部 Python 工具测试不计入游戏内通知，它们在游戏外运行。

## 添加未来测试

1. 在 `tools/test_sources/` 新增 `tca_<模块>_tests.txt`，各用例名称使用唯一的 tca_test_ 前缀。
2. 使用 name → assert → 一组或多组 effect/expect 的结构，可在步骤间加入整数 `wait_days = 1..30`。先 assert 场景，再自行准备独立状态，至少一个 expect；当前编译器不支持 character_target、target 等原生测试附加字段，遇到这些字段会明确报错。通过 title 等显式作用域定位对象，在 effect 中保存作用域。
3. 运行 `python3 tools/build_test_events.py`。工具自动发现所有 `tools/test_sources/tca_*_tests.txt`，生成各组事件和总调度列表，并按实际用例数计算计划数量。无需修改决议、通知、总入口或手填计数。生成文件开头有来源标记，不直接编辑。
4. 运行 `python3 tools/build_test_events.py --check` 只读检查是否已生成最新版本；运行相关工具测试。重启游戏加载新增事件，再使用相同的一键入口。

每个来源最多 99 项。各组事件命名空间由文件名去掉 _tests 后加 _test 派生，编号为文件内定义顺序；官制组使用 tca_court_test.1–13，司法法律组使用 tca_judicial_law_test.1–42，延迟组使用 tca_judicial_timing_test.1–4。新增用例尽量在文件末尾追加，不改变已有单项命令。禁止用例改写 tca_test_suite_* 统计变量和 tca_test_suite_running/tca_test_case_failed 运行标记。

生成器保留旧 `tools/build_court_test_events.py` 为兼容调用，实际生成范围同样是所有组。

## 延迟测试框架

`wait_days`编译为真正带days延迟的隐藏角色事件，不是直接调用正式worker或Python等待。继续事件沿用原事件保存的角色／头衔作用域，CHECK编号连续；任意阶段失败保留`tca_test_case_failed`，直到该用例最终结束才计为一个失败。来源前置不满足则计未执行并继续下一项。即时项全部结束后，四个延迟项串行准备／等待／断言，避免世界状态和保存作用域相互覆盖。暂停时不会完成等待，也不会提前出现全部通过。

总入口运行标记持续到最终汇总，等待时重复总入口只写SUITE_BUSY，不重置统计；同一测试请求角色在延迟阶段再调用单项入口只写CASE_BUSY，不覆盖失败标记。调试决议等待期间不可再次运行。单独执行延迟组单项时，只记录该项结果，不自动运行其他项或计入旧总入口。禁止在测试期间切换玩家人物或向其他人物启动第二套测试，跨角色并发不支持。测试请求角色死亡、游戏退出或延迟事件缺失时不会制造完成结果，日志核对仍报告缺项；重新启动专用新局再测试，不将测试运行中的存档用于正常游玩。
